At Rite Aid you ran SQL scripts to create test patients and find data problems. This week turns that into fluency: writing any query from scratch, quickly, while someone watches. That is what an interview SQL round tests.

Why testers need SQL

  • Verifying the backend. The UI says "Order placed". The database is where you confirm the right rows were written, with the right values.
  • Creating test data. Insert the exact patient, customer or order your test needs, instead of clicking through the UI for 10 minutes.
  • Finding defects the UI hides. Duplicate records, orphan rows, totals that don't add up.
  • Interviews. Almost every QA and SDET interview in India has at least one SQL question. Many have a full round.

About this databaseThe lessons run on SQLite inside your browser. The SQL you learn here is standard and works in MySQL, PostgreSQL and SQL Server. When MySQL behaves differently, a callout says so.

Your first query

SELECT chooses the columns. FROM names the table. Press Run:

SELECT * FROM customers;

* means "every column". It's fine for exploring a table, but in real queries, name the columns you need:

SELECT full_name, city FROM customers;

Aliases and calculated columns

You can compute new columns and rename them with AS. Here is each product's price with 18% GST added:

SELECT product_name,
       price,
       price * 1.18          AS price_with_gst,
       ROUND(price * 1.18, 2) AS rounded
FROM products;

DISTINCT removes repeated rows

SELECT DISTINCT city FROM customers;

DISTINCT applies to the whole row you select. SELECT DISTINCT city, loyalty_tier gives unique combinations, so a city can appear more than once.

Sorting with ORDER BY

SELECT product_name, category, price
FROM products
ORDER BY category ASC, price DESC;

ASC (A→Z, low→high) is the default. DESC reverses it. With several columns, the second only breaks ties in the first.

Limiting rows with LIMIT

SELECT product_name, price
FROM products
ORDER BY price DESC
LIMIT 3;

LIMIT 3 OFFSET 3 skips 3 rows and returns the next 3. This is how pagination works, and how you test it.

Common mistakeWithout ORDER BY, a database can return rows in any order, and the order can change between runs. If an automated test checks "the first row is X" without ORDER BY, it will become flaky. Always sort before you check position.
MySQL / SQL ServerMySQL uses LIMIT like SQLite. SQL Server uses SELECT TOP 3 ... or OFFSET 0 ROWS FETCH NEXT 3 ROWS ONLY.
Interview questions

Primary key vs foreign key? A primary key uniquely identifies a row in its own table: one per table, not NULL, unique. A foreign key is a column that references another table's primary key, to link records. A table can have many foreign keys.

Can a table have two primary keys? No. It has one primary key, but that key can be made of several columns (a composite key, e.g. (order_id, product_id)).

Primary key vs unique key? Both prevent duplicates. A table has only one primary key, and it can't be NULL. It can have many unique keys, and most databases allow NULL in a unique column.

Text values go in single quotes. Numbers don't need quotes.

MySQLIn SQLite, 'delivered' doesn't match 'Delivered'. In MySQL, the default text comparison usually ignores case, so it would match. Know which database you're testing against: a case bug can hide in one and show in the other.

Combining conditions: AND, OR, NOT

SELECT order_id, order_date, status, total_amount
FROM orders
WHERE status = 'Delivered' AND total_amount > 1000;
Common mistake: AND before OR

AND is evaluated before OR, just as × comes before + in maths. This query means "Critical defects that are Open, or any High defect", which is probably not what you wanted:

SELECT defect_id, severity, status
FROM defects
WHERE status = 'Open' AND severity = 'Critical' OR severity = 'High';

Use brackets to say what you mean:

SELECT defect_id, severity, status
FROM defects
WHERE status = 'Open' AND (severity = 'Critical' OR severity = 'High');

IN, BETWEEN, LIKE

IN is a short way of writing several ORs:

SELECT product_name, category FROM products
WHERE category IN ('Devices', 'Nutrition');

BETWEEN is inclusive at both ends:

SELECT order_id, order_date FROM orders
WHERE order_date BETWEEN '2025-03-01' AND '2025-03-31';

Dates here are stored as text like '2025-03-15'. That format sorts correctly as text, so comparisons work.

Date trap in MySQLIf a MySQL column is DATETIME, BETWEEN '2025-03-01' AND '2025-03-31' stops at 2025-03-31 00:00:00 and misses everything later on 31 March. The safe pattern is col >= '2025-03-01' AND col < '2025-04-01'. This is a real defect source, and a good interview point.

LIKE matches patterns. % means any number of characters; _ means exactly one:

SELECT full_name, email FROM customers
WHERE full_name LIKE 'A%';      -- names starting with A
SELECT product_name FROM products
WHERE product_name LIKE '%Monitor%';   -- contains "Monitor"

Text after -- is a comment. SQL ignores it.

NULL: missing values

NULL means "no value / unknown". It is not zero and not an empty string. You can't compare it with =. Run this. It returns nothing, even though one customer has no email:

SELECT full_name, email FROM customers WHERE email = NULL;

The correct way:

SELECT full_name, email FROM customers WHERE email IS NULL;

Use IS NOT NULL for the opposite. You'll see why = NULL fails in Lesson 5.

Interview questions

Difference between = NULL and IS NULL? Any comparison with NULL gives "unknown", which WHERE treats as false. So = NULL never matches. IS NULL is the operator built for this check.

Is BETWEEN inclusive? Yes, at both ends.

What do % and _ mean in LIKE? % is zero or more characters; _ is exactly one.

GROUP BY: one result row per group

SELECT module, COUNT(*) AS defects
FROM defects
GROUP BY module
ORDER BY defects DESC;

Group by more than one column to get one row per combination:

SELECT module, severity, COUNT(*) AS defects
FROM defects
GROUP BY module, severity
ORDER BY module, defects DESC;
The GROUP BY ruleEvery column in SELECT must either be in GROUP BY or be inside an aggregate. SELECT module, title, COUNT(*) ... GROUP BY module makes no sense: which title should it show for a module with 6 defects? SQLite quietly picks one. MySQL 8 (with ONLY_FULL_GROUP_BY, the default) and most other databases give an error.

HAVING: filtering groups

WHERE filters rows before grouping. HAVING filters groups after aggregation. Modules with more than 3 defects:

SELECT module, COUNT(*) AS defects
FROM defects
GROUP BY module
HAVING COUNT(*) > 3;

Both together: count only unresolved defects, then keep modules with 2 or more:

SELECT module, COUNT(*) AS open_defects
FROM defects
WHERE status <> 'Closed'
GROUP BY module
HAVING COUNT(*) >= 2;

The order SQL actually runs in

You write SELECT first, but the database runs it in this order. Learn it; it explains many errors.

1. FROM / JOIN    which rows exist
2. WHERE          keep some rows
3. GROUP BY       make groups
4. HAVING         keep some groups
5. SELECT         compute columns and aliases
6. DISTINCT
7. ORDER BY       sort (aliases work here)
8. LIMIT / OFFSET

This is why you can't use a SELECT alias inside WHERE in most databases: WHERE runs before SELECT has created it.

Interview questions

WHERE vs HAVING? WHERE filters individual rows before grouping and can't use aggregates. HAVING filters groups after GROUP BY and usually uses aggregates. You can use both in one query.

COUNT(*) vs COUNT(column) vs COUNT(1)? COUNT(*) and COUNT(1) both count all rows, with the same performance in modern databases. COUNT(column) counts only rows where that column is not NULL.

What's the logical order of SQL execution? FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.

Real data is split across tables. An order row stores customer_id = 4, not "Sneha Iyer". A JOIN puts the pieces back together. JOINs are the most important topic in SQL interviews, so this lesson is the longest of the week.

INNER JOIN: only rows that match

SELECT o.order_id, o.order_date, c.full_name, o.total_amount
FROM orders AS o
INNER JOIN customers AS c
        ON c.customer_id = o.customer_id
ORDER BY o.order_id;
  • o and c are table aliases. They make queries shorter and tell you which table each column comes from.
  • ON gives the matching rule, usually foreign key = primary key.
  • JOIN on its own means INNER JOIN.

Count the rows. There are 20 orders, but the result has 19. Order 1015 is missing. Its customer_id is 99, and no customer 99 exists. INNER JOIN drops rows that have no match. Your first orphan record.

LEFT JOIN: keep everything from the left table

LEFT JOIN keeps every row from the left table. Where there's no match on the right, the right-side columns are NULL.

SELECT c.customer_id, c.full_name, o.order_id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
ORDER BY c.customer_id;

Rahul (11) and Isha (12) appear with NULL order_id: they never ordered. This leads to one of the most useful patterns in SQL:

The "find what's missing" pattern

SELECT c.customer_id, c.full_name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;

LEFT JOIN, then keep rows where the right side is NULL. That gives you "customers without orders", "products never sold", "orders without payment" and "items pointing to deleted orders". Testers use this pattern all the time.

RIGHT and FULL OUTER JOIN

RIGHT JOIN is the mirror image: it keeps every row from the right table. Most people rewrite it as a LEFT JOIN with the tables swapped, which is easier to read. FULL OUTER JOIN keeps unmatched rows from both sides:

SELECT c.customer_id, c.full_name, o.order_id, o.customer_id AS order_customer
FROM customers c
FULL OUTER JOIN orders o ON o.customer_id = c.customer_id
WHERE c.customer_id IS NULL OR o.order_id IS NULL;

One query shows both problems: customers with no orders, and the order whose customer doesn't exist.

MySQLMySQL has no FULL OUTER JOIN. The usual workaround is a LEFT JOIN UNION a RIGHT JOIN. Expect this as an interview follow-up.

Joining three or more tables

Add one JOIN per table. Each order line with the customer name and product name:

SELECT o.order_id, c.full_name, p.product_name,
       oi.quantity, oi.unit_price,
       oi.quantity * oi.unit_price AS line_total
FROM orders o
JOIN customers c    ON c.customer_id = o.customer_id
JOIN order_items oi ON oi.order_id   = o.order_id
JOIN products p     ON p.product_id  = oi.product_id
ORDER BY o.order_id;

Self join: a table joined to itself

employees.manager_id points to another row in the same table. Use two aliases:

SELECT e.full_name AS employee, m.full_name AS manager
FROM employees e
LEFT JOIN employees m ON m.emp_id = e.manager_id;

It's a LEFT JOIN so that Lakshmi, who has no manager, still appears.

CROSS JOIN: every combination

A CROSS JOIN pairs every row with every other row, with no ON clause. Testers use it to build test matrices. For example, every payment method for every product category:

SELECT DISTINCT p.category, pay.method
FROM products p
CROSS JOIN payments pay
ORDER BY 1, 2;
Two classic JOIN bugs

1. A WHERE clause that undoes your LEFT JOIN. If you filter the right table in WHERE (e.g. WHERE o.status = 'Delivered'), the NULL rows are removed and you get an INNER JOIN again. Put the condition in ON instead:

-- keeps all customers; counts only their delivered orders
SELECT c.full_name, COUNT(o.order_id) AS delivered_orders
FROM customers c
LEFT JOIN orders o
       ON o.customer_id = c.customer_id AND o.status = 'Delivered'
GROUP BY c.customer_id, c.full_name
ORDER BY delivered_orders;

2. Fan-out. Joining orders to order_items repeats each order once per item. If you then SUM(o.total_amount), you count orders twice or three times. Always ask yourself what one row of the joined result represents.

Interview questions

Explain the types of joins. INNER: matching rows only. LEFT: all left rows plus matches (NULLs where none). RIGHT: the mirror of LEFT. FULL: all rows from both sides. CROSS: every combination. SELF: a table joined to itself, using aliases.

Table A has 5 rows, B has 3. Maximum rows from a CROSS JOIN? From an INNER JOIN? CROSS gives exactly 15. INNER can return anything from 0 to 15, depending on duplicate keys. This one is asked often; answer it calmly.

How do you find records in A that are not in B? LEFT JOIN B and check B.key IS NULL, or use NOT EXISTS (Week 2).

For every product category, the number of units sold (sum of quantity) across all orders except Cancelled ones. Categories with no sales should show 0. (Hint: start FROM products, so every category appears.)

FROM products p

This lesson covers the tools that make queries useful in practice: handling NULLs, if/else logic with CASE, and functions for text and dates. With these you can build reports that managers actually read.

Why NULL behaves strangely

SQL uses three-valued logic: TRUE, FALSE and UNKNOWN. Any comparison with NULL is UNKNOWN, and any arithmetic with NULL gives NULL:

SELECT NULL = NULL      AS eq,
       NULL <> 1        AS neq,
       10 + NULL        AS plus,
       NULL IS NULL     AS is_null;

WHERE keeps only TRUE rows, so UNKNOWN rows disappear quietly. That's why = NULL returns nothing.

COALESCE and NULLIF

COALESCE(a, b, c) returns the first value that isn't NULL. Use it to show a default:

SELECT full_name,
       COALESCE(email, 'missing')     AS email,
       COALESCE(loyalty_tier, 'None') AS tier
FROM customers;

NULLIF(a, b) returns NULL when a = b. Its main use is avoiding divide-by-zero: x / NULLIF(y, 0).

MySQLIFNULL(a, b) works in MySQL and SQLite; SQL Server uses ISNULL(a, b). COALESCE works in all of them. Prefer it.

CASE: if/else inside a query

SELECT product_name, price,
       CASE
         WHEN price < 300  THEN 'Budget'
         WHEN price < 1500 THEN 'Mid-range'
         ELSE 'Premium'
       END AS price_band
FROM products
ORDER BY price;

Conditions are checked from top to bottom, and the first true one wins. Without ELSE, unmatched rows get NULL.

Conditional aggregation: the reporting technique

Put CASE inside SUM or COUNT to count several things in one pass. A defect dashboard with one row per module:

SELECT module,
       COUNT(*)                                              AS total,
       SUM(CASE WHEN status <> 'Closed' THEN 1 ELSE 0 END)  AS unresolved,
       SUM(CASE WHEN severity = 'Critical' THEN 1 ELSE 0 END) AS critical,
       SUM(CASE WHEN severity = 'Critical' AND status <> 'Closed' THEN 1 ELSE 0 END) AS blockers
FROM defects
GROUP BY module
ORDER BY blockers DESC, unresolved DESC;

This is the query behind most "defect summary" slides. If you can write this in an interview, you stand out.

JOIN     b ON b.key = a.key             -- 1. combine

Missing rows      → LEFT JOIN … WHERE right.key IS NULL
Duplicates        → GROUP BY key HAVING COUNT(*) > 1
Counts per type   → SUM(CASE WHEN … THEN 1 ELSE 0 END)
NULL default      → COALESCE(col, 'default')

How to approach any SQL question

  1. What is one row of the answer? One customer? One month? One module?
  2. Which tables hold the data? Write the FROM and the JOINs first.
  3. Which rows count? Write the WHERE.
  4. Group and aggregate, then HAVING if needed.
  5. Check the result against a number you can count by hand. Testers have an advantage here: you already think about edge cases (NULLs, duplicates, no matches).

The drill

Top 3 customers by total order value, counting every order except Cancelled ones. Show name and total.

Show answer
SELECT c.full_name, SUM(o.total_amount) AS total
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
WHERE o.status <> 'Cancelled'
GROUP BY c.customer_id, c.full_name
ORDER BY total DESC
LIMIT 3;

Revenue per product category from Delivered orders only, using line items (quantity × unit_price).

Show answer
SELECT p.category, SUM(oi.quantity * oi.unit_price) AS revenue
FROM order_items oi
JOIN orders o   ON o.order_id = oi.order_id
JOIN products p ON p.product_id = oi.product_id
WHERE o.status = 'Delivered'
GROUP BY p.category
ORDER BY revenue DESC;

Customers who have bought from more than one product category.

Show answer
SELECT c.full_name, COUNT(DISTINCT p.category) AS categories
FROM customers c
JOIN orders o       ON o.customer_id = c.customer_id
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p     ON p.product_id = oi.product_id
GROUP BY c.customer_id, c.full_name
HAVING COUNT(DISTINCT p.category) > 1;

Unresolved defects per assignee, with unassigned defects grouped under Unassigned. Busiest first.

Show answer
SELECT COALESCE(assigned_to, 'Unassigned') AS assignee, COUNT(*) AS unresolved
FROM defects
WHERE status <> 'Closed'
GROUP BY assignee
ORDER BY unresolved DESC;

Which month had the most orders? Return just that month and its count.

Show answer
SELECT strftime('%Y-%m', order_date) AS month, COUNT(*) AS orders
FROM orders
GROUP BY month
ORDER BY orders DESC
LIMIT 1;

Interview follow-up: "What if two months tie?" LIMIT 1 hides the tie. You'll fix this with RANK in Week 2.

Cities with more than one customer.

Show answer
SELECT city, COUNT(*) AS customers
FROM customers
GROUP BY city
HAVING COUNT(*) > 1;

Average order value per loyalty tier (treat a missing tier as None). Exclude cancelled orders. Round to 2 decimals.

Show answer
SELECT COALESCE(c.loyalty_tier, 'None') AS tier,
       ROUND(AVG(o.total_amount), 2)    AS avg_order
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
WHERE o.status <> 'Cancelled'
GROUP BY tier
ORDER BY avg_order DESC;

Employees who earn more than their manager.

Show answer
SELECT e.full_name, e.salary, m.full_name AS manager, m.salary AS manager_salary
FROM employees e
JOIN employees m ON m.emp_id = e.manager_id
WHERE e.salary > m.salary;

This is one of the most frequently asked SQL interview questions anywhere. Now you know it.

Rapid-fire theory: say each answer aloud in under 30 seconds

DISTINCT vs GROUP BY? Both can remove duplicates. GROUP BY also lets you aggregate per group.

Can you use an alias in WHERE? Not in standard SQL, because WHERE runs before SELECT. You can use it in ORDER BY. (SQLite and MySQL allow aliases in HAVING; don't rely on that.)

What does a LEFT JOIN return when nothing matches? The left row, with NULL in every right-side column.

How would you check a UI order total against the database? Find the order by its ID, compare total_amount, and also recompute it from order_items to catch header/line mismatches.
