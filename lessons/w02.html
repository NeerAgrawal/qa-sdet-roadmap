A subquery is a query inside another query. A CTE (Common Table Expression) gives a subquery a name so you can read the logic from top to bottom. Together they let you break a hard question into small steps, which is exactly what interviewers want to see you do.

Subquery that returns one value

Products that cost more than the average product:

SELECT product_name, price
FROM products
WHERE price > (SELECT AVG(price) FROM products)
ORDER BY price DESC;

The inner query runs first and returns one number. The outer query uses it like a constant.

Subquery that returns a list: IN

SELECT full_name
FROM customers
WHERE customer_id IN (SELECT customer_id FROM orders WHERE status = 'Cancelled');

EXISTS and NOT EXISTS

EXISTS asks "is there at least one matching row?" and stops as soon as it finds one. Customers who placed an order worth more than ₹1,500:

SELECT c.full_name
FROM customers c
WHERE EXISTS (
  SELECT 1 FROM orders o
  WHERE o.customer_id = c.customer_id
    AND o.total_amount > 1500
);

The inner query refers to c from the outer query. That makes it a correlated subquery: conceptually it runs once for each customer.

The NOT IN trap: a favourite interview question

If the list inside NOT IN contains even one NULL, the whole condition becomes UNKNOWN and no rows come back. Vikram (Hyderabad) has a NULL email. Watch what happens:

SELECT full_name
FROM customers
WHERE email NOT IN (SELECT email FROM customers WHERE city = 'Hyderabad');

Zero rows, with no error. NOT EXISTS doesn't have this problem, so prefer it for "not in" logic:

SELECT c.full_name
FROM customers c
WHERE NOT EXISTS (
  SELECT 1 FROM customers h
  WHERE h.city = 'Hyderabad' AND h.email = c.email
);

Correlated subquery for "compared with its own group"

Orders bigger than that same customer's average order:

SELECT o.order_id, o.customer_id, o.total_amount
FROM orders o
WHERE o.total_amount > (
  SELECT AVG(o2.total_amount)
  FROM orders o2
  WHERE o2.customer_id = o.customer_id
);

Subquery in FROM (derived table)

SELECT tier, ROUND(AVG(spent)) AS avg_spent_per_customer
FROM (
  SELECT COALESCE(c.loyalty_tier, 'None') AS tier, c.customer_id, SUM(o.total_amount) AS spent
  FROM customers c
  JOIN orders o ON o.customer_id = c.customer_id
  GROUP BY c.customer_id
) AS per_customer
GROUP BY tier;

CTEs: the same idea, but readable

WITH name AS (...) defines a named result you can use in the query below it. Here is the derived table above rewritten as a CTE:

WITH per_customer AS (
  SELECT c.customer_id,
         COALESCE(c.loyalty_tier, 'None') AS tier,
         SUM(o.total_amount) AS spent
  FROM customers c
  JOIN orders o ON o.customer_id = c.customer_id
  GROUP BY c.customer_id
)
SELECT tier, ROUND(AVG(spent)) AS avg_spent_per_customer
FROM per_customer
GROUP BY tier;

You can chain several CTEs, separated by commas, each one using the ones before it. In interviews, CTEs make your thinking visible, and that earns marks.

Recursive CTEs: generating rows

A recursive CTE refers to itself. Testers use it to generate test data or a calendar. Here is every month of 2025 with its order count, including months with zero orders, which a plain GROUP BY can't show:

WITH RECURSIVE months(m) AS (
  SELECT '2025-01-01'
  UNION ALL
  SELECT date(m, '+1 month') FROM months WHERE m < '2025-12-01'
)
SELECT strftime('%Y-%m', m) AS month, COUNT(o.order_id) AS orders
FROM months
LEFT JOIN orders o ON strftime('%Y-%m', o.order_date) = strftime('%Y-%m', m)
GROUP BY month
ORDER BY month;
MySQLCTEs and recursive CTEs need MySQL 8.0 or later. Many companies still run 5.7. If WITH fails there, use a derived table instead.
Interview questions

Subquery vs JOIN: which is faster? It depends. Modern optimisers often turn one into the other. Use whichever states the question most clearly, and check the execution plan if performance matters.

What is a correlated subquery? A subquery that uses a column from the outer query, so it is evaluated for each outer row.

IN vs EXISTS? IN compares a value against a list. EXISTS checks whether any row exists and stops at the first match. NOT EXISTS is safe with NULLs; NOT IN isn't.

What is a CTE and why use one? A named, temporary result defined with WITH. It makes queries easier to read and lets you reuse a step. Recursive CTEs can walk hierarchies or generate rows.

Window functions are the topic that separates "knows SQL" from "is good at SQL" in interviews. They calculate across a set of related rows without collapsing them the way GROUP BY does. You keep every row and get a group-level number next to it.

The idea: OVER()

Compare each employee's salary with their department's average, keeping every row:

SELECT full_name, dept, salary,
       ROUND(AVG(salary) OVER (PARTITION BY dept)) AS dept_avg,
       salary - ROUND(AVG(salary) OVER (PARTITION BY dept)) AS diff
FROM employees
ORDER BY dept, salary DESC;
  • OVER (...) turns an aggregate into a window function.
  • PARTITION BY dept is like GROUP BY, but the rows are kept.
  • OVER () with nothing inside uses the whole table as one window.

Ranking: ROW_NUMBER, RANK, DENSE_RANK

The difference only shows up when there are ties. Asha and Gauri both earn 150,000; Sana and Kiran both earn 185,000:

SELECT full_name, salary,
       ROW_NUMBER() OVER (ORDER BY salary DESC) AS row_num,
       RANK()       OVER (ORDER BY salary DESC) AS rnk,
       DENSE_RANK() OVER (ORDER BY salary DESC) AS dense_rnk
FROM employees;
FunctionOn a tieSequence example
ROW_NUMBER()different numbers anyway (arbitrary)1, 2, 3, 4
RANK()same number, then skips1, 2, 2, 4
DENSE_RANK()same number, no gap1, 2, 2, 3

Top-N per group

Highest-paid person in each department. You can't filter a window function in WHERE, because it's calculated after WHERE runs. Wrap it in a CTE first:

WITH ranked AS (
  SELECT full_name, dept, salary,
         RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk
  FROM employees
)
SELECT dept, full_name, salary
FROM ranked
WHERE rnk = 1;

Support returns two people because Nisha and Tarun tie. With ROW_NUMBER you'd get only one of them, picked arbitrarily. In an interview, saying "do you want ties included?" shows maturity.

LAG and LEAD: looking at the previous or next row

For each customer, the previous order date and the number of days since it:

SELECT customer_id, order_id, order_date,
       LAG(order_date) OVER (PARTITION BY customer_id ORDER BY order_date) AS prev_order,
       julianday(order_date)
         - julianday(LAG(order_date) OVER (PARTITION BY customer_id ORDER BY order_date)) AS days_since_prev
FROM orders
ORDER BY customer_id, order_date;

LEAD() looks at the next row instead. Typical uses: change between releases, time between status changes, finding gaps in sequences.

Running totals and moving averages

Add ORDER BY inside OVER and SUM becomes cumulative:

SELECT order_date, order_id, total_amount,
       SUM(total_amount) OVER (ORDER BY order_date, order_id) AS running_total
FROM orders
WHERE status = 'Delivered';

A frame limits the window to nearby rows. Here is a 3-order moving average:

SELECT order_date, total_amount,
       ROUND(AVG(total_amount) OVER (ORDER BY order_date
                                     ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 2) AS moving_avg_3
FROM orders
WHERE status = 'Delivered';

NTILE and percent of total

SELECT product_name, price,
       NTILE(4) OVER (ORDER BY price) AS price_quartile,
       ROUND(100.0 * price / SUM(price) OVER (), 1) AS pct_of_catalogue
FROM products;
MySQLWindow functions need MySQL 8.0+. In 5.7, interviewers expect the older workaround with a self-join or a correlated subquery. Know that it exists, even if you'd never choose it.
Interview questions

Difference between RANK, DENSE_RANK and ROW_NUMBER? Give the 1-2-2-4 / 1-2-2-3 / 1-2-3-4 example. Then say which you'd use for "Nth highest salary" (DENSE_RANK) and for removing duplicates (ROW_NUMBER).

GROUP BY vs window function? GROUP BY returns one row per group. A window function keeps every row and adds the group-level value next to it.

Why can't you use ROW_NUMBER in WHERE? Window functions are computed in the SELECT step, after WHERE. Wrap the query in a CTE or subquery and filter outside it.

UPDATE and DELETE

The habit that saves careersBefore any UPDATE or DELETE, run a SELECT with the same WHERE and check the row count. An UPDATE without WHERE changes every row in the table.
-- 1. check what will change
SELECT product_id, product_name, is_active FROM products WHERE product_id = 108;

-- 2. change it
UPDATE products SET is_active = 1 WHERE product_id = 108;
SELECT product_id, product_name, is_active FROM products WHERE product_id = 108;
DELETE FROM customers WHERE full_name LIKE 'QA_AUTO_%';
SELECT COUNT(*) AS remaining_test_users FROM customers WHERE full_name LIKE 'QA_AUTO_%';

Test data habits

  • Use a recognisable prefix such as QA_AUTO_ or a test-run ID on every record you create, so cleanup is one safe DELETE.
  • Use IDs in a reserved range (e.g. 500+) or let the database generate them.
  • Clean up after yourself in a teardown step. In Week 3 this becomes a pytest fixture that inserts the data, yields it to the test, and deletes it afterwards.
  • Never run UPDATE or DELETE on production. Read-only access is the norm for testers there.

Transactions

A transaction groups changes so they all happen or none do. ROLLBACK undoes everything since BEGIN; COMMIT makes it permanent.

BEGIN;
INSERT INTO orders (order_id, customer_id, order_date, status, total_amount)
VALUES (5000, 1, date('now'), 'Placed', 70);
INSERT INTO order_items (item_id, order_id, product_id, quantity, unit_price)
VALUES (5000, 5000, 101, 2, 35);
SELECT * FROM orders WHERE order_id = 5000;
ROLLBACK;
SELECT COUNT(*) AS still_there FROM orders WHERE order_id = 5000;

The insert was visible inside the transaction and gone after ROLLBACK. Some test frameworks wrap every test in a transaction and roll it back, which keeps the database clean automatically.

Indexes

An index is like a book's index: it lets the database find rows without reading the whole table. Ask SQLite how it would run a query:

EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE customer_id = 4;

SCAN orders means it reads every row. Add an index and ask again:

CREATE INDEX IF NOT EXISTS idx_orders_customer ON orders(customer_id);
EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE customer_id = 4;

Now it says SEARCH … USING INDEX. Indexes speed up reads but slow down writes slightly and take space. Interviewers like it when you mention both sides.

Interview questions

DDL vs DML vs DCL vs TCL? DDL defines structure (CREATE, ALTER, DROP, TRUNCATE). DML changes data (INSERT, UPDATE, DELETE). DCL controls access (GRANT, REVOKE). TCL controls transactions (COMMIT, ROLLBACK, SAVEPOINT).

Clustered vs non-clustered index? A clustered index decides the physical order of the rows; there's one per table, usually the primary key. A non-clustered index is a separate structure that points to the rows; a table can have many.

How do you manage test data? "I create it with SQL or API calls in setup, tag it with a run-specific prefix, and delete it in teardown. For shared environments I avoid modifying data other teams depend on. At Rite Aid I created test patients with SQL scripts and…" Use your own experience.

This is the lesson that makes you valuable on a project. Backend or database testing means checking that the data is right, not just that the screen looks right. Our practice database has defects planted in it. By the end of this lesson you will have found all of them, and written each check so it can run automatically.

The rule: a check returns the failing rows

Write every validation query so that zero rows = PASS. Then automating it is trivial: run the query and assert the result is empty. If it isn't, the rows it returned are your defect evidence.

The six kinds of data checks

DimensionQuestionSQL pattern
CompletenessIs anything missing?COUNT source vs target; IS NULL on required fields
UniquenessIs anything duplicated?GROUP BY … HAVING COUNT(*) > 1
ValidityAre values allowed?WHERE col NOT IN (allowed list), ranges, formats
Referential integrityDoes every reference point to something real?LEFT JOIN … IS NULL
ConsistencyDo related numbers agree?Header total vs sum of lines; payment vs order
Timeliness / logicDo dates and states make sense?Closed without closed date; end before start

Worked examples

Completeness: required fields

SELECT customer_id, full_name, email
FROM customers
WHERE email IS NULL OR TRIM(email) = '';

Validity: values outside the allowed list

SELECT order_id, status
FROM orders
WHERE status NOT IN ('Placed','Shipped','Delivered','Cancelled','Returned');

Zero rows: PASS. Not every check finds something, and that's the point.

Referential integrity: orphans on both sides

SELECT 'order without customer' AS issue, o.order_id AS id
FROM orders o LEFT JOIN customers c ON c.customer_id = o.customer_id
WHERE c.customer_id IS NULL
UNION ALL
SELECT 'item without order', oi.item_id
FROM order_items oi LEFT JOIN orders o ON o.order_id = oi.order_id
WHERE o.order_id IS NULL;

Consistency: reconciliation

Does each order's total_amount equal the sum of its line items? Use LEFT JOIN so orders with no items are caught too, and compare with a small tolerance, because money stored as decimals can round:

SELECT o.order_id,
       o.total_amount,
       COALESCE(SUM(oi.quantity * oi.unit_price), 0) AS items_total
FROM orders o
LEFT JOIN order_items oi ON oi.order_id = o.order_id
GROUP BY o.order_id, o.total_amount
HAVING ABS(o.total_amount - COALESCE(SUM(oi.quantity * oi.unit_price), 0)) > 0.01;

Three failures, each a different bug: 1003 has a duplicated line, 1010's header is wrong, and 1017 has no lines at all.

Source-to-target testing (migrations and ETL)

When data moves from one system to another, you prove nothing was lost or changed. Let's simulate a buggy migration:

DROP TABLE IF EXISTS orders_target;
CREATE TABLE orders_target AS SELECT * FROM orders WHERE order_id <> 1009;  -- a row is lost
UPDATE orders_target SET total_amount = 800 WHERE order_id = 1010;          -- a value changes
SELECT (SELECT COUNT(*) FROM orders) AS source_rows,
       (SELECT COUNT(*) FROM orders_target) AS target_rows;

Counts catch the lost row but not the changed value. EXCEPT compares complete rows:

SELECT 'in source, not in target' AS side, * FROM (SELECT * FROM orders EXCEPT SELECT * FROM orders_target)
UNION ALL
SELECT 'in target, not in source', * FROM (SELECT * FROM orders_target EXCEPT SELECT * FROM orders);
MySQLEXCEPT and INTERSECT arrived in MySQL 8.0.31. On older versions, use a LEFT JOIN on the key and compare each column. Your Beyond Compare work at Sydney Water was the same idea applied to payloads; mention that link in interviews.

Turning checks into automated tests

This is a preview of Week 3. Each query becomes one pytest test, and the failing rows appear in the failure message:

import sqlite3   # use pymysql / mysql-connector for MySQL
import pytest

CHECKS = {
    "orphan_order_items": """
        SELECT oi.item_id FROM order_items oi
        LEFT JOIN orders o ON o.order_id = oi.order_id
        WHERE o.order_id IS NULL""",
    "duplicate_emails": """
        SELECT email FROM customers WHERE email IS NOT NULL
        GROUP BY email HAVING COUNT(*) > 1""",
}

@pytest.fixture(scope="session")
def db():
    conn = sqlite3.connect("shop.db")
    yield conn
    conn.close()

@pytest.mark.parametrize("name", CHECKS)
def test_data_check(db, name):
    rows = db.execute(CHECKS[name]).fetchall()
    assert rows == [], f"{name} failed for: {rows}"

Run it nightly in CI and you have a data-quality monitor. That's a strong project to describe in an interview.

Interview questions

How do you test a database / what is backend testing? Verify that UI and API actions write the correct data, then check integrity (keys and orphans), uniqueness, required fields, allowed values, and consistency between related tables. For migrations: counts, then a full row comparison, then spot checks on key business fields.

How would you test an ETL job? Check source vs target counts, use EXCEPT or a row-by-row comparison, check that transformation rules were applied correctly, check NULLs and defaults, duplicates, rejected records, and run time against the SLA.

You placed an order in the UI. What would you check in the database? The order header (customer, status, total, timestamps), the line items (products, quantities, prices, totals that reconcile), the payment row, stock reduction, the audit or log entries, and that no duplicate order was created on a double click. That last one was a real Critical defect in our table, #12.

WHERE NOT EXISTS (SELECT 1 FROM order_items oi WHERE oi.order_id = o.order_id);

Delivered orders that have no successful payment.

Show answer
SELECT o.order_id, o.total_amount
FROM orders o
WHERE o.status = 'Delivered'
  AND NOT EXISTS (
    SELECT 1 FROM payments p
    WHERE p.order_id = o.order_id AND p.status = 'Success'
  );

Order 1013 has a Failed payment and a Success payment (a retry), so it correctly passes. Only checking "has a payment row" would miss 1007 if it had a failed one.

Successful payments whose amount doesn't match the order total.

Show answer
SELECT p.payment_id, p.order_id, p.amount, o.total_amount
FROM payments p
JOIN orders o ON o.order_id = p.order_id
WHERE p.status = 'Success'
  AND ABS(p.amount - o.total_amount) > 0.01;

Order 1018 was undercharged by ₹9. Note that 1010 passes this check, because its payment matches its wrong header. Only the line-item reconciliation catches 1010. One check is never enough.

Defects whose status and closed date disagree: Closed with no closed_on, or not Closed but with a closed_on.

Show answer
SELECT defect_id, status, closed_on
FROM defects
WHERE (status = 'Closed' AND closed_on IS NULL)
   OR (status <> 'Closed' AND closed_on IS NOT NULL);

Line items sold at a price different from the product's current price. Is every result a defect? Think before you answer.

Show answer
SELECT oi.item_id, oi.order_id, p.product_name, oi.unit_price, p.price
FROM order_items oi
JOIN products p ON p.product_id = oi.product_id
WHERE oi.unit_price <> p.price;

Zero rows here. In a real system, though, prices change over time, so a mismatch might be correct historical data. A good tester checks the business rule before raising a defect. Say this in interviews.

Capstone: write one query that produces a data health report, with one row per check and its number of failures. Include at least: orders without customer, items without order, duplicate emails, missing emails, header/line mismatches, delivered-but-unpaid, and payment mismatches.

Show answer
SELECT 'orders_without_customer' AS check_name, COUNT(*) AS failures
FROM orders o LEFT JOIN customers c ON c.customer_id = o.customer_id WHERE c.customer_id IS NULL
UNION ALL
SELECT 'items_without_order', COUNT(*)
FROM order_items oi LEFT JOIN orders o ON o.order_id = oi.order_id WHERE o.order_id IS NULL
UNION ALL
SELECT 'duplicate_emails', COUNT(*)
FROM (SELECT email FROM customers WHERE email IS NOT NULL GROUP BY email HAVING COUNT(*) > 1)
UNION ALL
SELECT 'missing_emails', COUNT(*) FROM customers WHERE email IS NULL
UNION ALL
SELECT 'header_line_mismatch', COUNT(*)
FROM (SELECT o.order_id FROM orders o LEFT JOIN order_items oi ON oi.order_id = o.order_id
      GROUP BY o.order_id, o.total_amount
      HAVING ABS(o.total_amount - COALESCE(SUM(oi.quantity * oi.unit_price), 0)) > 0.01)
UNION ALL
SELECT 'delivered_unpaid', COUNT(*)
FROM orders o WHERE o.status = 'Delivered'
  AND NOT EXISTS (SELECT 1 FROM payments p WHERE p.order_id = o.order_id AND p.status = 'Success')
UNION ALL
SELECT 'payment_mismatch', COUNT(*)
FROM payments p JOIN orders o ON o.order_id = p.order_id
WHERE p.status = 'Success' AND ABS(p.amount - o.total_amount) > 0.01;

Classic query questions

Nth highest salary. Find the 3rd highest distinct salary. Interviewers often ask for three different ways.

Show answer

1. LIMIT/OFFSET (simple, but you must remember DISTINCT):

SELECT DISTINCT salary FROM employees ORDER BY salary DESC LIMIT 1 OFFSET 2;

2. DENSE_RANK (best: handles ties and returns the people):

WITH r AS (SELECT full_name, salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk FROM employees)
SELECT full_name, salary FROM r WHERE rnk = 3;

3. Correlated subquery (works on any database, even without window functions):

SELECT DISTINCT e.salary
FROM employees e
WHERE 2 = (SELECT COUNT(DISTINCT e2.salary) FROM employees e2 WHERE e2.salary > e.salary);

For N, the number in method 3 is N−1.

Delete duplicates, keeping one. Make a copy of customers, then delete duplicate emails from the copy, keeping the row with the lowest id.

Show answer
DROP TABLE IF EXISTS customers_copy;
CREATE TABLE customers_copy AS SELECT * FROM customers;

DELETE FROM customers_copy
WHERE email IS NOT NULL
  AND customer_id NOT IN (
    SELECT MIN(customer_id) FROM customers_copy
    WHERE email IS NOT NULL
    GROUP BY email
  );

SELECT customer_id, full_name, email FROM customers_copy ORDER BY customer_id;

The ROW_NUMBER version is also worth knowing:

DELETE FROM customers_copy
WHERE customer_id IN (
  SELECT customer_id FROM (
    SELECT customer_id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY customer_id) AS rn
    FROM customers_copy WHERE email IS NOT NULL
  ) WHERE rn > 1
);

Department with the highest average salary. Show the department and its average.

Show answer
WITH d AS (
  SELECT dept, AVG(salary) AS avg_sal FROM employees GROUP BY dept
)
SELECT dept, ROUND(avg_sal) AS avg_salary
FROM d
WHERE avg_sal = (SELECT MAX(avg_sal) FROM d);

Using = MAX rather than LIMIT 1 returns every department if there's a tie.

Customers whose every order was Delivered (and who have at least one order).

Show answer
SELECT c.customer_id, c.full_name, COUNT(*) AS orders
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.customer_id, c.full_name
HAVING SUM(CASE WHEN o.status <> 'Delivered' THEN 1 ELSE 0 END) = 0;

Pivot: one row per month, with columns for the number of Delivered, Cancelled and Other orders.

Show answer
SELECT strftime('%Y-%m', order_date) AS month,
       SUM(CASE WHEN status = 'Delivered' THEN 1 ELSE 0 END) AS delivered,
       SUM(CASE WHEN status = 'Cancelled' THEN 1 ELSE 0 END) AS cancelled,
       SUM(CASE WHEN status NOT IN ('Delivered','Cancelled') THEN 1 ELSE 0 END) AS other
FROM orders
GROUP BY month
ORDER BY month;

Each customer's most recent order, with its date and amount. Include only customers who have orders.

Show answer
WITH r AS (
  SELECT o.*, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_date DESC) AS rn
  FROM orders o
)
SELECT customer_id, order_id, order_date, total_amount
FROM r
WHERE rn = 1
ORDER BY customer_id;

Running total per customer: each order with the customer's cumulative spend up to that order.

Show answer
SELECT customer_id, order_id, order_date, total_amount,
       SUM(total_amount) OVER (PARTITION BY customer_id ORDER BY order_date) AS cumulative
FROM orders
ORDER BY customer_id, order_date;

Managers and team size: list each manager with the number of direct reports and their team's average salary. Biggest team first.

Show answer
SELECT m.full_name AS manager,
       COUNT(e.emp_id) AS direct_reports,
       ROUND(AVG(e.salary)) AS team_avg_salary
FROM employees m
JOIN employees e ON e.manager_id = m.emp_id
GROUP BY m.emp_id, m.full_name
ORDER BY direct_reports DESC;

Theory: model answers

QuestionModel answer
UNION vs UNION ALLUNION removes duplicate rows (slower, since it has to sort or hash). UNION ALL keeps everything. Use UNION ALL unless you need duplicates removed.
DELETE vs TRUNCATE vs DROPDELETE removes chosen rows, is logged, and can be rolled back. TRUNCATE removes all rows quickly and resets identity. DROP removes the table itself.
Primary vs unique keyOne primary key per table, never NULL. Many unique keys are allowed, and they usually allow NULL.
What is normalisation?Organising tables to reduce duplication. 1NF: atomic values, no repeating groups. 2NF: no partial dependency on part of a composite key. 3NF: no column depends on another non-key column.
What is denormalisation?Deliberately duplicating data to make reads faster, as in reporting tables. It's a trade-off: faster reads, harder consistency, more data checks to write.
What is a view?A saved query that behaves like a table. Useful for simplifying complex joins and limiting what users can see.
Stored procedure vs functionA procedure runs a set of statements and can change data. A function returns a value and can be used inside SELECT.
CHAR vs VARCHARCHAR is fixed length (padded). VARCHAR is variable length and uses only the space it needs.
What is an index; downsides?A structure that speeds up lookups. Downsides: slower INSERT and UPDATE, extra storage, and a poorly chosen index may never be used.
ACIDAtomicity, Consistency, Isolation, Durability. Explain each in one line (see Lesson 3).
What is SQL injection, and how do you test for it?Untrusted input changing a query, e.g. ' OR '1'='1 in a login field. Test input fields and APIs with such payloads and check that errors aren't leaked. The fix is parameterised queries.
