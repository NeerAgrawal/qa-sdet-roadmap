Selenium 4.6 and later include Selenium Manager, which finds or downloads the right driver for your browser automatically. You no longer download chromedriver by hand or use webdriver-manager.

How Selenium WebDriver works

your test (Python)
   │  driver.find_element(By.ID, "login-button").click()
   ▼
Selenium client library (language bindings)
   │  HTTP request with JSON, following the W3C WebDriver standard
   ▼
browser driver (chromedriver / msedgedriver / geckodriver)
   │  native browser automation
   ▼
the browser (Chrome / Edge / Firefox)

Every command is an HTTP call to the driver, which controls the browser and returns a response. That's why each step takes milliseconds, and why the browser and your test can get out of step: the root cause of most flaky tests.

Interview: Selenium 3 vs Selenium 4

Selenium 4 uses the W3C WebDriver standard directly (the old JSON Wire Protocol is gone), so behaviour is more consistent across browsers. It adds Selenium Manager for drivers, relative locators, new_window() for tabs and windows, element screenshots, Chrome DevTools / WebDriver BiDi access (network, console logs), and a redesigned Grid that can run as standalone, hub-and-node, or fully distributed, with Docker support.

Headless gotchaHeadless browsers often start with a small default window, so responsive layouts hide elements and tests fail only in CI. Always set a window size in headless mode.

find_element vs find_elements

find_element raises NoSuchElementException when nothing matches. find_elements returns an empty list and never raises. Use that to check that something is absent:

badges = driver.find_elements(By.CLASS_NAME, "shopping_cart_badge")
assert badges == []          # cart is empty: the badge isn't rendered at all
Interview questions

Explain Selenium WebDriver architecture. Client bindings send W3C WebDriver commands over HTTP to a browser-specific driver, which controls the browser natively and returns the result.

close() vs quit()? close shuts the current window; quit ends the session, closes all windows and stops the driver process. Use quit in teardown.

What can't Selenium do? Desktop apps, CAPTCHAs and OTPs (by design), image or visual comparison on its own, and native mobile apps (that's Appium). It also has no built-in reporting or test runner; you add pytest or TestNG.

get() vs navigate().to()? In Java, navigate() keeps browser history for back and forward; get() is the usual way to open a page. In Python, driver.get() is the only one.

Most flaky and high-maintenance UI tests come down to poor locators. A good locator is unique, stable when the layout changes, and readable. This lesson gives you a priority order, cheat sheets for CSS and XPath, and techniques for dynamic pages.

Locator priority

  1. A test attribute such as data-test, data-testid or data-qa, added for automation. Sauce Demo has these. In your project, ask developers to add them; it's a common, reasonable request.
  2. id, if it's stable. Avoid generated ones like input-38f2a.
  3. name for form fields.
  4. CSS selector built on stable attributes.
  5. Relative XPath, when you need text matching or to move up the tree.
  6. Never absolute XPath (/html/body/div[2]/div/form/input[1]) or positions that change when the layout changes.

The eight By strategies: ID, NAME, CLASS_NAME, TAG_NAME, LINK_TEXT, PARTIAL_LINK_TEXT, CSS_SELECTOR, XPATH.

Check locators in DevTools first

Press F12, open the Console tab and try your locator before writing code:

$$("[data-test='login-button']")     // CSS: returns the matching elements
$x("//input[@id='user-name']")       // XPath

Exactly one match is what you want. Zero means the locator is wrong; several means it's too loose.

Dynamic elements: anchor and traverse

When an element has no stable attribute, find a stable neighbour (usually visible text) and move from there. On The Internet's /tables page, the amount due for Jason Doe:

from selenium import webdriver
from selenium.webdriver.common.by import By

driver = webdriver.Chrome()
try:
    driver.get("https://the-internet.herokuapp.com/tables")
    due = driver.find_element(
        By.XPATH,
        "//table[@id='table1']//td[text()='Jason']/following-sibling::td[2]",
    ).text
    assert due == "$100.00", due
finally:
    driver.quit()

It reads as "in table 1, find the cell 'Jason', then the second cell after it". The row order can change and this still works.

Relative locators (Selenium 4)

from selenium.webdriver.support.relative_locator import locate_with

password = driver.find_element(locate_with(By.TAG_NAME, "input").below({By.ID: "user-name"}))

Also above, to_left_of, to_right_of and near. They're handy for forms without good attributes, but they depend on layout, so use them sparingly.

Interview questions

CSS vs XPath? CSS is generally faster, shorter and consistent across browsers. XPath can match text and move to parents and ancestors. Prefer CSS; use XPath when you need text or upward traversal.

How do you handle dynamic IDs? Use a stable part with starts-with/contains (or CSS ^=/*=), anchor on nearby stable text and traverse, or ask developers for a data-testid.

Absolute vs relative XPath? Absolute starts at /html and breaks on any layout change; relative starts with // and targets attributes or text.

Most flaky Selenium tests are timing problems: the test acts before the page is ready. This lesson is the most important one this week, and the one interviewers press hardest on.

Three kinds of wait

ImplicitExplicitFluent
Set withdriver.implicitly_wait(10)WebDriverWait(driver, 10).until(cond)WebDriverWait with poll_frequency and ignored_exceptions
Applies toevery find_element for the whole sessionone specific conditionone specific condition
Waits forthe element to exist in the DOMany condition: visible, clickable, text, URL…same, with your own polling and ignore rules
Use it?avoid in frameworksyes, the defaultwhen you need custom polling
Never mix implicit and explicit waitsThe Selenium documentation warns against it: the two interact, and total wait times become unpredictable. A 10s implicit wait plus a 15s explicit wait can take far longer than either. Pick explicit waits and set implicit to 0 (the default).
time.sleep() is not a waitsleep(5) always costs 5 seconds, and it still fails when the page needs 6. A suite full of sleeps is slow and flaky at the same time.

Explicit waits in practice

from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC

wait = WebDriverWait(driver, 10)
button = wait.until(EC.element_to_be_clickable((By.ID, "checkout")))
button.click()

until checks the condition every 0.5s. It returns as soon as the condition holds (usually with the element), or raises TimeoutException after 10s.

Presence is not visibility: a live demonstration

On /dynamic_loading/1, the "Hello World!" element is in the page from the start, but hidden. A presence wait succeeds immediately, before the text is visible:

from selenium import webdriver
from selenium.webdriver.common.by import By
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC

driver = webdriver.Chrome()
try:
    driver.get("https://the-internet.herokuapp.com/dynamic_loading/1")
    driver.find_element(By.CSS_SELECTOR, "#start button").click()

    present = WebDriverWait(driver, 10).until(EC.presence_of_element_located((By.ID, "finish")))
    print("presence:", repr(present.text))        # '' : hidden elements have no visible text

    shown = WebDriverWait(driver, 10).until(EC.visibility_of_element_located((By.ID, "finish")))
    print("visibility:", repr(shown.text))        # 'Hello World!'
    assert shown.text == "Hello World!"
finally:
    driver.quit()

Waiting for the wrong condition is a classic cause of tests that pass on a fast laptop and fail in CI.

Fluent wait and custom conditions

from selenium.common.exceptions import NoSuchElementException, StaleElementReferenceException

wait = WebDriverWait(
    driver, timeout=15, poll_frequency=0.25,
    ignored_exceptions=[NoSuchElementException, StaleElementReferenceException],
)

# a condition is just a function that takes the driver and returns something truthy
rows = wait.until(lambda d: d.find_elements(By.CSS_SELECTOR, ".result-row") if len(d.find_elements(By.CSS_SELECTOR, ".result-row")) >= 3 else False)

# or a readable named function
def cart_count_is(n):
    def _check(d):
        badges = d.find_elements(By.CLASS_NAME, "shopping_cart_badge")
        return (int(badges[0].text) if badges else 0) == n
    return _check

wait.until(cart_count_is(2))

ExceptionUsual causeFix
NoSuchElementExceptionwrong locator; element not loaded yet; it's inside an iframecheck in DevTools; explicit wait; switch to the frame
TimeoutExceptionthe wait condition never became truewrong condition (presence vs visibility) or a real bug; read the screenshot
StaleElementReferenceExceptionthe page re-rendered after you found the element (React/Angular, refresh, AJAX)find it again just before using it; don't store elements for long; wait for staleness_of
ElementClickInterceptedExceptionsomething covers it: spinner, cookie banner, sticky header, animationwait for the overlay to be invisible; scroll it into view; close the banner. A JS click is a last resort, because it skips what a real user would hit.
ElementNotInteractableExceptionelement is hidden, disabled or zero-sizedwait for visible or clickable; interact with the visible control instead

Interview questions

Implicit vs explicit vs fluent wait? Use the table above, then say "I use explicit waits inside BasePage helpers and keep implicit at zero, because mixing them makes timings unpredictable".

How do you handle StaleElementReferenceException? Explain the cause (the DOM node was replaced), then the fix: locate again just before acting; helpers take locators, not elements; a wait that ignores stale exceptions while the page re-renders.

Your test passes locally and fails in CI. How do you debug it? Read the failure screenshot and logs; look for timing (headless is faster or slower), window size, test data shared between parallel runs, and environment differences. Fix the cause; don't add sleeps or retries.

Scenario question: "Clicking Checkout throws ElementClickInterceptedException about 1 run in 10." Give three possible causes and the right fix for each.

Show answer
  • A loading overlay or spinner is still fading out → wait for invisibility_of_element_located on the overlay before clicking.
  • A sticky header or cookie banner covers the button after scrolling → close the banner in setup; scroll the element to the centre (scrollIntoView({block: 'center'})).

pages/base_page.py

from selenium.common.exceptions import TimeoutException
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.support.ui import WebDriverWait

import config


class BasePage:
    PATH = "/"

    def __init__(self, driver, timeout=10):
        self.driver = driver
        self.wait = WebDriverWait(driver, timeout)

    def open(self):
        self.driver.get(config.BASE_URL + self.PATH)
        return self

    def find(self, locator):
        return self.wait.until(EC.visibility_of_element_located(locator))

    def find_all(self, locator):
        return self.driver.find_elements(*locator)

    def click(self, locator):
        self.wait.until(EC.element_to_be_clickable(locator)).click()

    def type(self, locator, text):
        field = self.find(locator)
        field.clear()
        field.send_keys(text)

    def text_of(self, locator):
        return self.find(locator).text

    def is_visible(self, locator, timeout=2):
        try:
            WebDriverWait(self.driver, timeout).until(EC.visibility_of_element_located(locator))
            return True
        except TimeoutException:
            return False

Every helper takes a locator, not an element, and finds it fresh each time. That design removes most stale-element errors.

The page classes

# pages/login_page.py
from selenium.webdriver.common.by import By

from pages.base_page import BasePage
from pages.inventory_page import InventoryPage


class LoginPage(BasePage):
    PATH = "/"
    USERNAME = (By.ID, "user-name")
    PASSWORD = (By.ID, "password")
    SUBMIT = (By.ID, "login-button")
    ERROR = (By.CSS_SELECTOR, "[data-test='error']")

    def login(self, username, password):
        self.type(self.USERNAME, username)
        self.type(self.PASSWORD, password)
        self.click(self.SUBMIT)

    def login_as(self, username, password):
        """Successful login: returns the next page, so tests can chain."""
        self.login(username, password)
        return InventoryPage(self.driver).wait_until_loaded()

    def error_message(self):
        return self.text_of(self.ERROR)
# pages/inventory_page.py
from selenium.webdriver.common.by import By
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.support.ui import Select

from pages.base_page import BasePage


class InventoryPage(BasePage):
    PATH = "/inventory.html"
    TITLE = (By.CLASS_NAME, "title")
    NAMES = (By.CLASS_NAME, "inventory_item_name")
    PRICES = (By.CLASS_NAME, "inventory_item_price")
    BADGE = (By.CLASS_NAME, "shopping_cart_badge")
    CART_LINK = (By.CLASS_NAME, "shopping_cart_link")
    SORT = (By.CSS_SELECTOR, "[data-test='product-sort-container']")

    def wait_until_loaded(self):
        self.wait.until(EC.url_contains(self.PATH))
        self.find(self.TITLE)
        return self

    def product_names(self):
        return [e.text for e in self.find_all(self.NAMES)]

    def product_prices(self):
        return [float(e.text.replace("$", "")) for e in self.find_all(self.PRICES)]

    def add_to_cart(self, slug):
        self.click((By.CSS_SELECTOR, f"[data-test='add-to-cart-{slug}']"))

    def remove_from_cart(self, slug):
        self.click((By.CSS_SELECTOR, f"[data-test='remove-{slug}']"))

    def cart_count(self):
        badges = self.find_all(self.BADGE)
        return int(badges[0].text) if badges else 0

    def sort_by(self, value):          # 'az', 'za', 'lohi', 'hilo'
        Select(self.find(self.SORT)).select_by_value(value)

    def open_cart(self):
        from pages.cart_page import CartPage    # local import avoids a circular import
        self.click(self.CART_LINK)
        return CartPage(self.driver)

conftest.py: the driver fixture

from pathlib import Path

import pytest
from selenium import webdriver

SCREENSHOTS = Path(__file__).parent / "screenshots"


def pytest_addoption(parser):
    parser.addoption("--browser", default="chrome", choices=["chrome", "edge", "firefox"])
    parser.addoption("--headless", action="store_true", help="run without a visible window")


def make_driver(name, headless):
    if name == "chrome":
        options = webdriver.ChromeOptions()
    elif name == "edge":
        options = webdriver.EdgeOptions()
    else:
        options = webdriver.FirefoxOptions()
    if headless:
        options.add_argument("--headless=new" if name != "firefox" else "-headless")
    options.add_argument("--window-size=1366,768")
    factory = {"chrome": webdriver.Chrome, "edge": webdriver.Edge, "firefox": webdriver.Firefox}
    return factory[name](options=options)


@pytest.fixture
def driver(request):
    drv = make_driver(request.config.getoption("--browser"), request.config.getoption("--headless"))
    yield drv
    drv.quit()


@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    """After each test's main phase, save a screenshot if it failed."""
    outcome = yield
    report = outcome.get_result()
    if report.when == "call" and report.failed:
        drv = item.funcargs.get("driver")
        if drv is not None:
            SCREENSHOTS.mkdir(exist_ok=True)
            drv.save_screenshot(str(SCREENSHOTS / f"{item.name}.png"))

The driver is function-scoped: every test gets a fresh browser. It's slower, but no test can affect another, and that is what makes parallel runs safe (Lesson 6). The hook is how pytest lets you act on a test's result. Interviewers ask about it ("How do you take screenshots on failure?").

Where Sauce Demo can changeThe locators here match Sauce Demo's current markup. Sites change; if a locator stops matching, check it in DevTools (Lesson 2) and update it in one page class. That single fix is the reason POM exists, and a good story to tell in interviews.
Interview questions

What is POM and why use it? One class per page, holding its locators and actions. Tests call methods, not locators. A UI change is fixed in one place; tests read like business steps; code is reused.

Should page objects contain assertions? Generally no: pages return data and tests assert on it. The exception is a "page loaded" check, as in wait_until_loaded.

Page Factory? A Java pattern (@FindBy with lazy initialisation). Python frameworks don't use it, and even in Java many teams have moved away from it because it can cause stale-element problems.

How do you take a screenshot on failure? A pytest pytest_runtest_makereport hook (a TestNG listener, ITestListener.onTestFailure, in Java) that saves the screenshot and attaches it to the report.

JavaScript alerts

Browser-native alerts block the page until handled. Custom HTML modals aren't alerts; you handle those as normal elements.

Frames

An iframe is a page inside a page. Selenium only sees one document at a time, so you must switch in, then switch back out:

from selenium import webdriver
from selenium.webdriver.common.by import By

driver = webdriver.Chrome()
try:
    driver.get("https://the-internet.herokuapp.com/nested_frames")
    driver.switch_to.frame("frame-top")           # by name or id
    driver.switch_to.frame("frame-middle")        # nested: switch again
    assert driver.find_element(By.ID, "content").text == "MIDDLE"

    driver.switch_to.parent_frame()               # up one level
    driver.switch_to.default_content()            # back to the main page
    driver.switch_to.frame("frame-bottom")
    assert driver.find_element(By.TAG_NAME, "body").text.strip() == "BOTTOM"
finally:
    driver.quit()

You can also switch with an element (switch_to.frame(driver.find_element(By.CSS_SELECTOR, "iframe"))), or wait and switch in one step with EC.frame_to_be_available_and_switch_to_it(locator).

Mouse and keyboard: ActionChains

from selenium import webdriver
from selenium.webdriver.common.action_chains import ActionChains
from selenium.webdriver.common.by import By
from selenium.webdriver.common.keys import Keys
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC

driver = webdriver.Chrome()
wait = WebDriverWait(driver, 10)
try:
    # hover
    driver.get("https://the-internet.herokuapp.com/hovers")
    first = driver.find_elements(By.CLASS_NAME, "figure")[0]
    ActionChains(driver).move_to_element(first).perform()
    caption = wait.until(EC.visibility_of(first.find_element(By.CSS_SELECTOR, ".figcaption h5")))
    assert caption.text == "name: user1"

    # right-click
    driver.get("https://the-internet.herokuapp.com/context_menu")
    ActionChains(driver).context_click(driver.find_element(By.ID, "hot-spot")).perform()
    alert = wait.until(EC.alert_is_present())
    assert alert.text == "You selected a context menu"
    alert.accept()

    # keyboard
    driver.get("https://the-internet.herokuapp.com/key_presses")
    driver.find_element(By.ID, "target").send_keys(Keys.SPACE)
    assert driver.find_element(By.ID, "result").text == "You entered: SPACE"

Why SPACE and not ENTER? On this page the box sits inside a form, so ENTER submits it and reloads the page. The result is then empty and the old element is stale. That's a real example of StaleElementReferenceException from Lesson 3.

Other actions: double_click, drag_and_drop(src, dst), click_and_hold, key_down(Keys.CONTROL) … key_up, scroll_to_element. Nothing happens until .perform().

Drag and drop that "does nothing"Many pages, including The Internet's /drag_and_drop, use HTML5 drag events, which Selenium's drag_and_drop doesn't trigger in Chrome. The usual workaround is a small JavaScript snippet that dispatches the drag events. Knowing this limitation is a strong interview answer.

Interview questions

How do you handle multiple windows? Store the original handle, wait for the window count, switch to the new handle, close it, and switch back.

What happens if you don't switch back after closing a window? The next command raises NoSuchWindowException.

How do you handle an element inside an iframe? Switch to the frame (by name, index or element, ideally with a wait), act, then default_content().

How do you upload a file? Download one? Upload: send_keys the path to the file input. Download: set the browser's download folder in options, then check that the file exists, or call the download URL directly with requests.

When do you use JavaScriptExecutor? Scrolling, reading page state, or hidden elements in specific cases. Not as the default click, because it bypasses what a real user experiences.

Grid modeWhat it is
StandaloneEverything in one process or container; ideal on a laptop or in simple CI

Parallel runs with pytest-xdist

pip install pytest-xdist
pytest -n 4 --headless       # 4 worker processes
pytest -n auto --headless    # one per CPU core

Parallel runs only work if the tests are independent:

  • a function-scoped driver (yours already is), so every test has its own browser
  • no test relies on another test having run first
  • no shared mutable test data: create unique data per test, e.g. f"qa_{uuid4().hex[:8]}"
  • files written with unique names (the screenshot hook uses the test name)

Flaky tests: how seniors handle them

  1. Measure. Re-run the suspect test 20 times (pytest --count=20 with pytest-repeat) to confirm it's flaky and see how often it fails.
  2. Find the cause. Read the screenshot and logs. It's usually a wait condition, test data collisions, test order, the environment, or animations.
  3. Fix the cause: a correct explicit wait, isolated data, better locators.
  4. Quarantine if you must. Mark it (@pytest.mark.flaky or a "quarantine" marker), raise a ticket, and keep it out of the release gate until it's fixed.
  5. Use retries carefully. pytest-rerunfailures (--reruns 1) hides symptoms. Track how many tests needed a rerun; if that number grows, the suite is degrading.
